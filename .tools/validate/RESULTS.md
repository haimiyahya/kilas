## Campaign outcome (2026-09-12)

- **Stack validated end-to-end.** All four user-named doubts resolved: (1) no usable tmpfs in PRoot — hot data stays in BEAM RAM (ETS/MemGit, 20× headroom); (2) DuckDB keeps up with rapid writes (batch ~10ms/edit, flat to 50k); (3) vector store = **DuckDB vss HNSW 3ms KNN @10k** (sqlite-vec+exqlite 9.7ms validated as fallback); (4) local embedding works (Ortex + real bge-micro-v2 INT8, 140MB RSS) but the 8–12ms/embed target holds only for small chunks — budget 15–35ms for 100–300-token chunks.
- **Preferred stack:** duckdbex NIF (precompiled, spec dep, vss loads through it, bulk 1.5µs/row) + inotify (`apt install inotify-tools`; `file_system` hex pkg verified working) + ETS/MemGit hot path + Ortex/tokenizers. Embedding store is plug-and-play (`vector_store.exs` behaviour): DuckDB vss or sqlite-vec vec0 interchangeable by config — identical results verified, pick per corpus size.
- **Build-system finding (corrected):** cargo/rustc DO work under this PRoot (initial "cargo broken" conclusion disproven). The real bug is version-specific: **newest proc-macro2 1.0.107 / quote 1.0.47** build-script binaries vanish between rustc child exit and cargo's link/copy → "failed to link or copy … No such file or directory" (reproduced anywhere those versions are used, incl. inside sqlitetds's tree; rustc proven to emit the binary — shim experiment). Pinning sqlitetds's known-good lock versions (**proc-macro2 =1.0.106, quote =1.0.46, syn =2.0.118**) makes every build succeed, incl. the full Rustler path. Also: `cargo new` needs `--vcs none` (git-lockfile rename ENOENT). Rustler NIF built via mix compile and benchmarked (row 13).
- Scripts in this dir are standalone `.exs`/`.sh`/`.py` reproducing every number above; `data/` and `models/` gitignored.
